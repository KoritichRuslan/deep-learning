## 2. Метрики й вартість

Правило рішення: прогноз «шахрайство», якщо `s ≥ t`. Для `t` визначаємо

- `TP` - шахрайські, позначені як шахрайські; `FP` - легітимні, позначені як шахрайські (хибні тривоги);
- `FN` - пропущені шахрайські; `TN` - легітимні, позначені як легітимні;
- `C(t) = 10·FN(t) + FP(t)`; `Amount` у вартість не входить;
- `precision = TP / (TP + FP)`, `recall = TP / (TP + FN)`. Якщо знаменник дорівнює нулю, метрика не визначена (н/в): `precision` - коли немає жодного позитивного рішення (наприклад `t = +inf`), `recall` - коли в вибірці немає позитивних міток.

## 3. Пошук порога

Кандидати: усі унікальні оцінки validation та `+inf` («усі негативні»; найменша оцінка означає «усі позитивні»). Рівні оцінки отримують однаковий прогноз, тому поріг, що відповідає групі рівних оцінок, враховує всю групу.

Алгоритм (`threshold.candidate_table`, `O(n log n)`):

1. Сортуємо оцінки за спаданням.
2. `cumsum(y)` дає `TP`, а `cumsum(1 − y)` дає `FP` для «перших k об'єктів».
3. Порогу `t = u` відповідають усі об'єкти з `s ≥ u`, тобто остання позиція групи рівних оцінок. Тому беремо лічильники лише там, де наступна оцінка менша (кінці груп); так рівні оцінки ніколи не розриваються.
4. `FN = P − TP`, `TN = N − FP`; додаємо рядок `+inf` (`TP = FP = 0`).
5. Рядки впорядковані за спаданням порога, тому `argmin` повертає перший мінімум, тобто **найбільший поріг** серед рівних за вартістю. Це й є `t*`.

Для кожного порога не виконується повторний прохід по вибірці. Повна таблиця кандидатів: `analysis/validation_candidates.csv` (`threshold, TP, FP, FN, TN, C`, без округлення; округлення лише в таблицях нижче). Додатково `analyze.py` порівнює швидкий пошук із прямим підрахунком `confusion()` на 300 випадкових порогах плюс крайні.

**Чому висока ROC-AUC не гарантує ні малої вартості, ні високої precision.**

1. ROC-AUC оцінює лише ранжування: ймовірність, що випадковий позитивний приклад отримає більшу оцінку, ніж випадковий негативний. Вона не залежить від вибору порога, тоді як вартість `C(t)` залежить від нього, від співвідношення цін `10 : 1` і від абсолютних кількостей помилок.
2. `FPR = FP / (FP + TN)` ділиться на всі негативні приклади (їх понад 56 тисяч на validation), тому навіть дуже малий `FPR` означає багато хибних тривог в абсолютних числах.
3. `precision = π·TPR / (π·TPR + (1 − π)·FPR)`, де `π` - частка шахрайства (~0.17%). За малого `π` навіть низький `FPR` може давати багато хибних тривог відносно істинних позитивних, тож precision залишається низькою за високої ROC-AUC. Для цієї задачі корисніша PR-крива, яка прив'язана до `π`.
4. AUC усереднює всі пороги, а вартість вимірюється в одній робочій точці.

## 4. Перевірка пошуку порога на наборах A, B, C

Незалежний еталон (`verify_threshold.brute_force`) - чистий Python без numpy: для кожного кандидата правило `s ≥ t` застосовується до кожного об'єкта окремо. Кандидати будуються окремо (унікальні оцінки + `+inf`), результати швидкого алгоритму для еталона не використовуються. Лічильники й `C` мають збігатися точно, вибраний поріг - відповідати тому самому правилу нічиєї. Додатково звіряємо з очікуваними значеннями, виведеними вручну: A - `t* = 0.4`, `C = 2`; B - `t* = +inf`, `C = 0`; C - `t* = 0.8`, `C = 10`.

Набір C (за умовою): оцінки `[0.8, 0.5 ×11, 0.2]`, мітки `[1, 1, 0 ×10, 0]`, тобто серед одинадцяти оцінок 0.5 перша має мітку 1, решта десять - 0.

Що перевіряє кожен набір:

- **A (рівні оцінки 0.7, 0.7 з різними мітками).** Прогноз для рівних оцінок має бути однаковим, тому кандидат `0.7` додає обидва об'єкти одночасно (`TP = 1`, `FP = 2`), і «розрізати» пару неможливо. Реалізація, яка рахує кумулятивні суми по кожному об'єкту й бере всі позиції, дала б неіснуючі проміжні стани.
- **B (немає позитивних міток).** `FN = 0` за будь-якого порога, `C = FP`, мінімум досягається на `+inf` («усі негативні», `C = 0`). Це перевіряє, що кандидат `+inf` присутній і виграє, а також що не виникає ділення на нуль (`recall` не визначений).
- **C (два кандидати з однаковою вартістю).** `C(0.8) = 10·1 + 0 = 10` і `C(0.5) = 10·0 + 10 = 10`. За умовою обираємо більший поріг, `0.8`. Це перевіряє правило нічиєї: `argmin` на спадному списку, а не на зростаючому.

## 6. Висновки

<!-- AUTO:summary_numbers -->
- validation: перехід від t=0.5 до t* змінив FN 27 → 16 (-11), FP 9 → 34 (+25), C 279 → 194 (-85); зміна вартості -30.5%.
- test: перехід від t=0.5 до t* змінив FN 28 → 19 (-9), FP 8 → 43 (+35), C 288 → 233 (-55); зміна вартості -19.1%.
- Базова лінія «усі негативні»: C = 10·P = 980 на validation і 990 на test.
<!-- /AUTO:summary_numbers -->

**Що змінив вибір порога у роботі незмінної моделі.** Ваги моделі, оцінки й ROC-/PR-криві лишились тими самими; змінилась лише точка на кривих, у якій ухвалюється рішення. Зниження порога від 0.5 до `t*` збільшує кількість позитивних рішень: частина пропущених шахрайств (`FN`) стає виявленою, але з'являється більше хибних тривог (`FP`). Через ціну `10 : 1` один виявлений пропуск виправдовує до десяти додаткових хибних тривог, тому мінімум вартості лежить у точці, де цей обмін перестає бути вигідним. Ціна рішення в термінах `FN` і `FP` наведена в блоці вище (зміни `FN`, `FP` і `C` на validation і test).

**Чому результат на validation не гарантує такого самого виграшу на test.** `t*` обрано за конкретною скінченною вибіркою, де шахрайських прикладів лише близько сотні. Вартість на скінченній вибірці є кусково-сталою функцією порога й змінюється лише на оцінках прикладів, тож мінімум визначається кількома випадковими прикладами (див. розкид `t*` у бутстрепі). Оптимальний на validation поріг частково підганяється під її шум, тому на test вартість зазвичай не така мала, як на validation, а вигода від зміни порога може бути іншою. Вибір кращого з двох порогів за test теж був би помилкою: тестова оцінка перестала б бути незалежною від вибору. Окремо слід пам'ятати, що оцінки моделі не обов'язково відкалібровані, а ціна `10 : 1` навчальна, не банківська.
